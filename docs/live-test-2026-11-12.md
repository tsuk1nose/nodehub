# Debian 13 / N2840 device validation

English | [简体中文](zh-CN/docs/live-test-2026-11-12.md)

Date: 2026-11-12, Asia/Taipei. These are temporary-center integration results, not complete production deployment acceptance. Actual device addresses, serials, domains, tokens, and private keys are omitted.

The **current model is automatic root SSH**. Earlier sections describe historical test stages, not current setup instructions.

## Initial upstream and terminal test

The test device was an Intel N2840 running Debian 13 x86_64, with ext4 root and an existing Btrfs `/data`. A unique serial became its hostname, Tailscale name, and MeshCentral display name.

Headscale enrollment/binding succeeded, assigned IPv4/IPv6 addresses, and appeared online in center polling. A new MeshCentral Login Token authenticated successfully; the intended group contained the online matching Agent, which was explicitly verified and bound. The rejected old token was not reused.

Repeated initialization reused the serial, Tailscale identity, and MeshAgent installation. The activation file was removed; independent recovery state remained root-owned mode 600.

The optional Agent connected as an independent system user with HTTPS/WSS and Ed25519 authentication. One service-memory observation was roughly 6 MB, not a long-term benchmark. A real Chromium browser signed in, opened the terminal, executed harmless system queries, resized, and closed without script/CSP errors. This first test used an existing explicitly authorized SSH key and did not add root SSH keys.

### Fixes found during integration

1. Headscale masks preauth keys in node reads. New records retain immutable preauth IDs; old pending records have a strictly validated masked-prefix compatibility check.
2. The supplied Linux MeshAgent binary requires `-install`. `-fullinstall` returned success without installation. The hook now uses the correct command and checks service activity.
3. SSHD offers multiple host keys. Negotiation must select the pinned key type rather than rejecting another legitimate key after negotiating it. Integration fixtures now offer multiple host keys.
4. Temporary HTTPS used P-256 for browser compatibility; the device's Ed25519 application identity is independent. Production certificates remain operator-managed.

Go race tests, static checks, and Python compilation passed after those fixes.

## Historical automatic maintenance-account test

The subsequent automatic-provisioning version used `nodehub-maint`; it has since been superseded by root terminals.

With no manual `terminal.nodes` targets or SSH-key mount, the center generated per-node keys in SQLite. The initializer created the maintenance account, installed its public authorization, confirmed installation, and started the Agent. That account had a nonzero UID, only its own group, and no added sudo privileges.

Its home/`.ssh` were root-owned mode 755, public authorization mode 644, and progress mode 600. Browser terminal commands returned the maintenance username and expected host information. Repeat initialization preserved both login-key and host-key digests and created no duplicate node.

After center restart, starting the Agent and waiting for readiness restored a working terminal from SQLite. A browser must wait for Agent online/refresh rather than assuming a fixed 30-second click timeout covers reconnection. Observed Agent service memory was about 6.2 MiB, not a capacity guarantee.

The full Go race/network suite passed, including automatic enrollment-to-terminal round trips. Temporary services were stopped; later testing migrated the same identity to root as below.

## Root terminal model acceptance

At the operator's request, the current automatic terminal logs in directly as root:

- New nodes no longer create a maintenance account. A serial-marked block is added to root `authorized_keys`, preserving unrelated authorization and avoiding duplicate blocks on retry.
- The existing test device migrated using the same SSH login key and host key. The center changed the target user only after root installation was confirmed.
- Real browser login, command output, resize, and close passed; `id -un` returned root. Repeat initialization passed.
- Checks confirmed the original root authorization remained intact, the Node Hub block was unique, and the exact old tool-managed maintenance authorization file was removed.
- The old account/directories were retained, not deleted. The Agent still runs unprivileged as a fixed local SSH relay; sshd executes the shell as root.
- Existing root-public-key policy is checked. If needed, a public-key-only root-login drop-in is added without granting new password access or replacing other keys.
- Full Go race/network tests, nine Python tests, and static checks passed. Coverage includes staged old-account migration, key preservation, root authorization blocks, idempotence, SSH policy, and response-loss recovery.

## Final test state and remaining deployment work

The temporary center and SSH loopback forwarding are stopped. The native Agent is installed, stopped, and disabled; Tailscale, MeshAgent, and SSH remain active. Root's Node Hub authorization is retained and pairs with the private key in the ignored temporary center database.

The recovery state and Agent identity still bind `https://localhost:18443`. Do not simply edit configuration or delete identity to move them. Preserve/back up the database and node state, then deliberately migrate the URL binding. There is no automated migration tool. A fresh independent deployment should use a clean new clone.

Runtime configuration and database are in ignored `tmp/live-test/`, excluded from Docker context and source distribution. Screenshots are also local ignored artifacts. No production credentials or actual deployment identifiers are recorded in public examples.

No finalization, OverlayFS activation, partition change, or device reboot was performed. The stage remains `awaiting_binding` despite both actual upstream bindings existing, because finalization is explicit. Device deep links, linked revocation, complete clone/OverlayFS startup, power-loss recovery, and `/data` mount-failure behavior remain pending.
