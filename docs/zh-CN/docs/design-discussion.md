## 1. 目标

实现一个中心管理程序，统一管理 Debian 13 边缘节点的初始化、身份和接入状态，将 Headscale 与 MeshCentral 的设备资料关联起来，并提供简单的管理 Web 界面。

职责初步划分：

| 组件 | 职责 |
| --- | --- |
| 中心管理程序 | 节点身份、注册编排、设备关联、状态汇总、管理入口 |
| Headscale + Tailscale 客户端 | 组网和网络访问 |
| MeshCentral + MeshAgent | 远程终端、文件操作和设备维护 |
| 初始化脚本 | 安装、领取配置、注册、验证和重试 |

## 2. 已提出的需求

### 2.1 服务器后端

- 对接 Headscale 和 MeshCentral 的管理接口。
- 边缘节点初始化时，为其分配唯一 ID。
- 协助节点完成 Headscale 和 MeshCentral 注册。
- 节点 ID（序列号）确定为 12 位 `0–9`、`A–Z` 组成的随机编号，数据库唯一约束兜底，碰撞重试。

### 2.2 管理 Web 界面

- 默认提供最简单的权限认证，并支持关闭。
- 实际部署计划前置 Authelia。
- 查看节点注册时间、最后一次上线时间、ID、Tailscale 地址等资料。
- 提供进入对应 MeshCentral 设备的按钮。
- 暂不代理或集成 MeshCentral 管理界面，仅提供对应设备的跳转入口。

### 2.3 边缘节点

- 目标系统为 Debian 13。
- 客户端工作以初始化脚本为主。
- 是否增加自有数据采集组件，暂不确定。
- 先完成其他程序的安装配置，最后安装配置初始化程序，再关机制作克隆镜像。
- 每台刷入镜像的节点首次启动后领取独立序列号，将 hostname 改为该序列号，并使用该序列号注册 Tailscale 和 MeshCentral。
- 初始化流程还需配置根目录 OverlayFS；`/data` 使用 CoW，具体文件系统待定，挂载失败不得阻止系统开机。
- Tailscale、MeshAgent 等服务凭据及状态在初始化期间写入根目录下各自默认位置，不迁移至 `/data`；完成后作为根目录持久基线保留。
- 初始化成功后、启用 OverlayFS 并重启之前，删除初始化凭据、脚本或程序及其首次启动服务。失败恢复与删除过程必须可重试；清理完成后不再自动发起首次注册。
- 可在中心确认本机独立凭据有效且恢复流程可用后提前删除本机初始化凭据；这是建议清理顺序，具体恢复认证协议待定。批量令牌不会因为一台设备成功而全局失效。

### 2.4 部署与存储

- 服务端提供 Docker 部署文件和启动脚本，建议使用 Docker Compose 编排。
- Headscale、MeshCentral 与中心服务先同机以 Docker 部署，后期按实际情况拆分。确定使用 Headscale 内置 DERP 并启用客户端准入校验，不为该校验额外部署 Tailscale 容器。未来如需服务端主动访问 tailnet 节点，再按需求增加。边缘节点当前按 Debian 系统服务讨论。
- MeshCentral 版本固定为 **1.3.1**，接口与镜像待验证。
- Headscale 暂定目标版本为 **0.29.7**，这是指定的兼容目标，尚未验证该版本镜像及接口。
- **持续跟进项：Headscale 后续可能有破坏性更新，需要跟进并调整适配。** 不自动追随 `latest`，升级前验证接口、注册流程和数据迁移。
- 中心数据库暂定 **SQLite**，适配当前数据量较小的阶段；其他服务使用各自的存储配置。

## 3. 建议的第一版范围

以下为建议，待确认后作为实现范围。

1. 节点身份登记和查询。
2. 通过受控的初始化令牌注册节点。
3. 支持预装或首次启动时安装 Tailscale 和 MeshAgent，并以领取的序列号注册。
4. 保存中心节点与两个外部系统设备的对应关系。
5. 初始化支持重复执行、失败重试和部分成功后的继续执行。
6. 管理界面展示节点资料、两套系统的连接状态和注册错误。
7. 提供可关闭的本地管理员登录。
8. 提供 MeshCentral 对应设备的跳转入口。
9. 提供 Docker 部署文件、启动脚本、配置与持久化说明。
10. 支持克隆镜像首次启动初始化、hostname 设置及 OverlayFS 配置。

暂不纳入第一版的建议项：自研远程终端、文件传输、完整监控平台、自有常驻 agent，以及在中心页面重做 MeshCentral 全部功能。

## 4. 总体交互

```text
管理员浏览器 → Authelia / 反向代理 → 中心管理 Web 与后端
                                      ├─ Headscale 管理接口
                                      ├─ MeshCentral 管理接口
                                      └─ 中心数据库

Debian 初始化脚本 → 中心注册入口
Tailscale 客户端  → Headscale / 对等节点 / DERP
MeshAgent        → MeshCentral
管理员浏览器     → MeshCentral 对应设备页面
```

建议 MeshCentral 具备独立于 Tailscale 的公网连接入口，以便在组网配置失败时仍可远程维护。若两套服务共用同一主机或出口，它们仍存在共同故障点。

中心后端不转发所有节点业务流量，主要负责注册与管理信息。

## 5. 节点身份设计

### 5.1 建议方案

本文将“序列号”与“展示编号”视为同一字段，用作 hostname 和两个外部系统的设备名称；序列号字符集已确定为 `0–9`、`A–Z`，不另设内部 UUID；序列号直接作为中心节点唯一标识，不提供修改序列号功能。

将节点身份与认证凭据分开；节点唯一 ID、序列号与展示编号为同一字段：

| 字段 | 建议 | 用途 |
| --- | --- | --- |
| 节点 ID / 序列号 | 12 位 `0–9`、`A–Z` 随机字符串 | 中心唯一标识、数据库关联、设备命名和人工检索 |
| 注册令牌 | 独立的高强度随机凭据 | 允许设备发起初始化 |
| 节点凭据 | 若需要持续调用中心接口，再单独设计 | 后续上报或恢复操作认证 |

12 位编号共有 `36^12 = 4,738,381,338,321,616,896` 种组合。需使用安全随机数生成，并由数据库唯一约束兜底，发生碰撞时重新生成。编号不可作为认证秘密。

### 5.2 身份生命周期

- 节点首次注册后，将必要身份信息保存在本地。
- 重复运行初始化脚本，应优先恢复已有注册流程。
- 系统镜像中不得预置已注册节点的身份和密钥。
- 不以主机名、IP 地址或 MAC 地址作为唯一的身份判断依据。
- 不提供更换序列号或恢复旧档案的流程；需要重新建立身份时，重新注册为新节点并分配新序列号，保留旧节点档案。正常重启、网络重连及未完成初始化的重试继续使用现有身份。
- 不提供节点删除功能；旧档案及序列号保留，不重新分配。
- 本地身份文件的复制不能被视为正常的设备恢复；克隆冲突的检测与处理方式待定。

## 6. 初始化与注册流程

### 6.0 镜像制作与首次启动

镜像制作阶段：

1. 安装配置业务程序和系统依赖。
2. 最后安装配置初始化程序及首次启动服务；Tailscale / MeshAgent 可以预装，但不提前注册。
3. 封装为等待首次初始化的模板，清理设备专属状态后关机克隆。模板封装后再次开机可能触发初始化，需提供明确操作说明。

克隆设备首次启动阶段：

1. 在根目录持久可写、OverlayFS 尚未生效的阶段初始化；尝试挂载 `/data`，失败不得阻止系统开机。仅依赖 `/data` 的任务可进入降级或延后执行。
2. 在根目录保存本机初始化请求身份和步骤进度，再向中心领取序列号；超时或断电重试复用该身份。
3. 保存中心身份和序列号，将 hostname 改为序列号，并保持相关主机名配置一致。
4. 按下述子流程接入 Tailscale 与 MeshCentral，以序列号命名，状态与凭据保存在根目录各自默认位置。
5. 如需提前删除初始化凭据，先确认中心已建立本机独立认证，且该认证足以继续未完成的注册和清理；否则待注册成功后删除。
6. 确认配置和身份已经写入根目录持久基线，完成清理：删除初始化凭据、脚本或程序及首次启动服务，清理临时秘密。
7. 安排好无需初始化秘密的重启验证方式，启用 OverlayFS 并重启。实现时采用可恢复的最终化步骤，避免清理过程中断电后无从继续。
8. 验证 hostname、两个服务连接与身份保留。通过何种已有通道或独立验证任务确认完成，待实现前确定；不以保留完整初始化程序为前提。

注册完成与设备初始化完成分开记录，后者包括清理和 OverlayFS 重启验证。具体启动顺序待原型验证。

### 6.1 建议流程

1. 管理员在中心创建初始化令牌，有效期和允许注册次数均可自定义，并支持无限期、无限次数；早期使用无限期、无限次数，以复用已有镜像。
2. 在 Debian 节点运行初始化脚本，提交令牌并检查本地已有状态。
3. 中心校验令牌，创建或恢复节点注册记录，返回展示编号和当前注册进度。
4. 中心生成短期、不可复用的 Headscale 预认证密钥。
5. 脚本安装 Tailscale，并使用指定 Headscale 地址完成注册。
6. 脚本安装并注册 MeshAgent。
7. 中心分别确认两个外部系统中的设备，并保存关联。
8. 两项均确认成功后，将节点标记为注册完成。

Headscale 管理密钥和 MeshCentral 管理凭据只保存在服务器，不下发到边缘节点。

### 6.2 重试与部分成功

建议分别记录 Headscale、MeshCentral 两个步骤的状态，而不是只保存一个成功标记：

- 尚未开始。
- 正在处理。
- 已完成。
- 失败，附错误摘要及时间。

节点总体注册状态由两个步骤汇总。网络超时或脚本中断后，应检查实际结果再重试，避免重复创建设备。一个步骤成功、另一个失败时，保留已完成结果并允许继续执行。

令牌过期、恢复身份、同时重复执行和已使用令牌的重试策略，需要在接口设计阶段明确。

初始化令牌可作为镜像中的批量引导凭据，可撤销，期限与次数可分别设为无限。注册额度按新设备绑定计数，同一设备恢复不重复扣次数；不得将整个批量令牌绑定到第一台设备后停用。镜像不包含中心管理密钥或已注册设备身份。本机删除令牌不影响其他镜像副本使用。

### 6.3 OverlayFS 与持久化约束

- 初始化时根目录持久可写；身份、hostname、Tailscale / MeshAgent 默认状态目录及清理结果均在 OverlayFS 生效前写入底层持久基线。不得将初始化写入留在重启即丢弃的临时上层。
- `/data` 使用 CoW，具体文件系统及挂载参数待定；不将 CoW 等同于根目录 OverlayFS。挂载失败不得阻止开机，不成为 Tailscale / MeshAgent 启动前提。
- 不涉及生产台的服务凭据不放 `/data`。生产台相关数据及客户端凭据的具体边界另行确定，不因未来采集草稿而自动调整现有服务目录。
- 需写 `/data` 的任务在挂载失败时降级或延后，不能误向根目录下同名空目录写入生产数据。
- hostname、SSH 主机密钥和 machine-id 在首次启动时独立生成或配置，根目录基线保留，模板不携带已注册身份。
- 初始化凭据若放根目录，必须在 OverlayFS 生效前删除；若放 `/data`，删除不会被根目录 OverlayFS 遮蔽，但仍须确认该挂载真实存在。
- 根目录基线保留的服务身份能跨重启恢复，但运行期密钥更新、重新登录、MeshAgent 更新等写入是否保留仍需设计维护模式，不能假设初始基线足以覆盖所有后续状态变化。
- upper/work 位置、是否内存写入、重启是否清空及根目录升级方式仍待确认。

### 6.4 待验证的关键点

- MeshAgent 的注册方式、安装参数和目标设备组选择。
- 如何可靠地将 MeshCentral Node ID 与中心节点绑定，不能仅按主机名匹配。
- Headscale 注册完成后，如何可靠获取对应节点 ID。
- 实际部署版本支持哪些管理接口及认证方式。
- Debian 13 目标 CPU 架构、安装依赖与服务启动行为。

## 7. 数据与状态展示

### 7.1 建议保存的节点资料

| 类别 | 字段 |
| --- | --- |
| 中心身份 | 节点 ID（即序列号 / 展示编号）、备注或名称 |
| 注册信息 | 中心首次注册时间、注册进度、步骤错误、最近更新时间 |
| Headscale 关联 | 外部节点 ID、节点名称、Tailscale IPv4 / IPv6、连接状态、上游可见时间 |
| MeshCentral 关联 | Node ID、设备组标识、连接状态、上游可见时间 |
| 同步信息 | 每个来源最近成功同步时间、同步错误 |

具体字段以实际接口能可靠提供的内容为准。中心首次注册时间由中心自己维护，不随上游设备重建而改写。

### 7.2 “在线”和“最后上线”的含义

建议分别显示 Headscale 与 MeshCentral 的状态，避免合并成一个含义不清的在线标记。

- 上游明确报告在线或离线时，记录其状态。
- 查询失败时，显示同步异常或未知，并保留上次成功同步时间。
- 上游提供的“最后可见时间”与中心观察到的“离线转在线时间”应区分存储。
- 如上游无法提供准确的历史上线时间，可显示中心最近观察到在线的时间，并明确标注。
- 中心周期查询两套上游的状态，间隔可配置，默认 **60 秒**。必须同时检测离线和重新上线，否则无法触发下一次上线资料刷新。
- 首次发现在线，以及每次离线转在线时，刷新一次节点基础资料；持续在线时以状态检查为主，不重复采集完整资料。基础资料限于现有上游可提供的信息，不引入自有长期采集。
- 中心首次启动、重启后或同步恢复时执行一次资料对齐；地址等易变字段可随上游状态响应更新，避免持续在线时展示过期资料。
- 能批量查询时按上游批量同步，不为每台设备创建独立轮询任务；重试有退避，查询失败不判定为节点离线。
- 60 秒是查询间隔，不保证实际上下线在 60 秒内被识别：还受上游状态判定及请求耗时影响，两次轮询之间的短暂上下线也可能无法捕获。

## 8. 管理界面与认证

### 8.1 页面建议

- 节点列表：展示编号、名称、两套连接状态、Tailscale 地址、注册时间、最后可见时间。
- 节点详情：完整关联信息、注册步骤、错误摘要、同步时间和 MeshCentral 入口。
- 初始化入口：创建注册令牌，提供对应的执行说明。

不提供节点删除功能。吊销访问仍按此前要求联动两个后台；身份重建通过受授权初始化创建新节点，不先删除旧档案。

### 8.3 节点生命周期联动（已确认）

- **吊销访问**：中心凭据失效，Headscale 与 MeshCentral 均执行对应的拒绝访问动作；不得只隐藏中心列表中的设备。具体上游动作按目标版本验证，不将删除设备记录作为本阶段功能。
- **重新注册**：重新执行受授权初始化，分配新的 12 位序列号，在两个上游注册为新节点。旧档案保留，不迁移旧身份。现场可能需要重新安装初始化工具或重新刷机。
- 重新注册本身不代表旧凭据已经吊销；需要停用旧身份时独立执行联动吊销。
- 联动吊销分别记录两个上游的结果、错误和重试进度；部分失败显示未完成，不误报成功。离线节点也必须在服务端阻止旧身份重新接入，具体能力待验证。
- 通用批量初始化令牌不因单台吊销而全局失效；持有该令牌的设备仍可能申请新身份，禁止再次注册属于额外授权策略。

## 9. MeshCentral 入口与集成层级

| 层级 | 内容 | 建议 |
| --- | --- | --- |
| 设备跳转 | 点击按钮进入 MeshCentral 对应设备 | 第一版优先，具体 URL 待验证 |
| 反向代理 | 由中心代理 MeshCentral 管理界面 | 当前不实现 |
| 页面嵌入 | 在中心页面嵌入 MeshCentral 界面 | 暂缓，需验证会话和页面限制 |
| 功能重做 | 在中心直接实现远程终端、文件等操作 | 暂不计划 |

“中心已登录”不自动意味着“MeshCentral 已登录”。两者的统一认证方案需要独立确认；不能只隐藏按钮来替代 MeshCentral 自身的权限检查。

**范围已明确：长期数据采集当前阶段不实现。** 未来方案见 [长期数据采集设计草稿](telemetry-draft.md)，不将其客户端、接口、存储或页面纳入当前开发范围。

Tailscale 支持 UDP 直连，也可在无法直连时经 DERP 中继；MeshCentral 使用 WebSocket 连接和中继。两者能覆盖大量常见 NAT 和出站网络环境，但严格白名单、代理认证、TLS 检查、长连接限制等场景仍需实测。

建议第一版不实现自己的常驻 agent，先使用 Tailscale 与 MeshAgent 的现有能力。待明确存在以下需求时，再评估增加采集组件：

- CPU、内存、磁盘等历史指标和告警。
- 自有业务服务的健康信息。
- 离线数据缓存和恢复后的补传。
- 本地自动修复任务。

少量周期上报可先采用 systemd timer 加短脚本；持续监控则另行评估专门的监控工具。MeshCentral 可提供的设备信息及其更新频率需要验证，不能直接当作完整监控能力。

## 11. 部署与实现方案

### 11.1 Docker 交付

- 提供中心服务 Dockerfile、Compose 编排、配置示例、启动脚本与部署说明。
- 覆盖中心服务、MeshCentral、Headscale，以及按实际用途确定的服务端 Tailscale 容器。
- 中心数据库和各外部服务数据分别挂载持久卷，容器重建不得丢失身份与关联信息。
- 当前不部署用于 DERP 校验的 Tailscale 容器。域名、证书和反向代理由用户负责，不纳入当前设计交付；应用提供可配置监听和上游地址。
- 固定服务版本，说明升级、备份、恢复和回退条件。

### 11.2 SQLite 方案

- 中心服务初始按单实例部署，SQLite 数据库置于持久卷，优先使用宿主机本地存储。
- 提供数据库迁移及一致性备份恢复方案，不能将运行中的数据库主文件简单复制视为完整备份。
- 后续按并发、写入量和多实例需求评估是否迁移数据库。

### 11.3 版本兼容

- Headscale 以 **0.29.7** 为暂定兼容目标，接口与镜像待验证。
- 管理接口集中在适配层，记录已验证版本。后续破坏性更新需跟进适配，升级前在测试环境验证注册、查询、设备关联与迁移。
- 文末旧版本注册资料仅作概念参考，不作为目标版本的接口契约。
- MeshCentral 固定 **1.3.1**，接口兼容与镜像待验证；Tailscale 版本尚待选择。

### 11.4 DERP 准入方案核对

已核对 Headscale **v0.29.7** 随版本文档：

- 内置 DERP 支持 `derp.server.verify_clients: true`，文档说明客户端校验默认开启，无需为了该校验再部署本地 tailscaled。
- 独立 Tailscale derper 可通过 `-verify-client-url` 指向 Headscale `/verify` 进行准入校验；需要明确设置 `-verify-client-url-fail-open=false`，避免 Headscale 不可达时放行未知客户端。实际 derper 版本须验证支持这些参数。
- 独立 derper 使用 `--verify-clients` 则通过本地 tailscaled 校验，需要配套 Tailscale 客户端及其 socket，并确保 ACL 允许看到需验证的节点。
- 上述是不同校验路径；Headscale 管理 API 的存在本身不要求服务端加入 tailnet。若中心需主动通过 Tailscale 地址探测或访问节点，服务端客户端另有用途。
- 已确认第一阶段采用 Headscale 内置 DERP，显式启用客户端校验。独立 derper 路径仅保留作未来参考，不作为本阶段部署选项。

来源：[v0.29.7 DERP 文档](https://github.com/juanfont/headscale/blob/v0.29.7/docs/ref/derp.md)、[Tailscale derper 参数](https://github.com/tailscale/tailscale/blob/main/cmd/derper/derper.go)。

### 11.5 已确认技术栈

- 后端：Go，使用标准库 `net/http` 提供 HTTP API，按需引入轻量路由库。
- 数据：SQLite，明确 SQL 和迁移管理，驱动在实现时选择。
- 前端：Vue 3 + TypeScript + Vite，采用成熟后台组件库，具体组件库待选择。
- 前端构建为静态资源，由 Go 服务提供；开发期前后端可分开运行，生产环境中心只需一个服务容器。
- Headscale、MeshCentral 对接分别放在独立适配模块；状态同步先在中心进程内执行，不引入消息队列或微服务。
- 上述技术选型已确认；当前仍处于文档对齐阶段。

### 11.6 规模与部署边界

- 初期几百台节点，CPU 以 x86 Intel N2840 为主；实际系统位数和安装包架构在部署验证时确认。Headscale 与 MeshCentral 目前均未部署，需要首次部署。按单实例中心和 SQLite 设计。未来可能增长到几千、几万台，本阶段不为远期规模引入集群、分库或队列。
- 各服务先同机部署，后期视情况分开；服务地址和凭据可配置，不硬编码同机假设。
- 域名、证书及反向代理由用户管理，本阶段不设计其部署方案。
- 状态查询默认每 60 秒一次，可配置，执行策略见 7.2。

### 11.7 上游管理凭据与服务地址（已确认）

这里指中心服务调用其他后台时使用的服务器侧凭据：

- Headscale 管理 API key：用于申请预认证密钥、查询节点等。
- MeshCentral 自动化管理账号或访问凭据：用于查询和管理设备，具体认证方式按 1.3.1 实际接口验证。

不指边缘节点的 Tailscale / MeshAgent 身份，也不指初始化令牌或 Web 管理员密码。

已确认采用配置文件：

- Headscale 管理 API key、MeshCentral 自动化账号或访问凭据均在中心配置文件中配置。
- Docker 容器间通信地址同样在配置文件中配置，包括中心访问 Headscale 和 MeshCentral 的内部地址；同机 Compose 部署可使用服务名，拆分部署后修改配置即可。
- 内部管理接口地址与下发给节点或浏览器使用的外部访问地址分开配置，不能将 Docker 内部服务名下发给边缘节点。
- 配置文件从宿主机只读挂载到中心容器，限制宿主机文件权限；提供不含真实秘密的配置示例。
- 凭据不写入源码、镜像、日志或浏览器响应，不下发到节点。
- 更换凭据或地址后修改配置并重启中心，当前不实现热重载或自动轮换。
- MeshCentral 具体认证字段及上游最小权限范围，在 1.3.1 接口验证后确定；不影响采用配置文件这一决定。

## 13. 实现前的验证与验收建议

先用一台 Debian 13 测试节点验证接口和关联方式，再确定实现细节。

- 首次执行能完成中心登记和两个系统注册。
- 同一模板刷出的多台设备获得不同序列号、设备密钥及系统身份。
- hostname、Tailscale 名称和 MeshCentral 设备名称对应序列号，验证上游对名称大小写的处理。
- 初始化过程中断电或断网后可恢复，不重复创建中心档案。
- OverlayFS 启用并重启后身份和注册关系保留，hostname 与两套服务连接正常。
- `/data` 挂载失败仍可正常开机，并使用根目录现有身份启动 Tailscale / MeshAgent；依赖 `/data` 的任务正确降级。
- 初始化清理后服务不再重跑，重启后底层初始化秘密不会重新出现。
- Docker 容器重建后数据保留，SQLite 备份可恢复。
- 完成指定 Headscale 版本的兼容性验证。
- 重复执行不会重复创建设备。
- 任一注册步骤失败后可以继续完成。
- 页面可正确区分节点离线与上游同步失败。
- MeshCentral 按钮能打开正确设备，权限由其自身校验。
- Authelia 开启时，浏览器管理入口受保护，机器连接仍可正常工作。
- 关闭 UDP 后验证 DERP 连通性，单独中断 Tailscale 后验证 MeshCentral 维护能力。
- 吊销联动两个上游；任一上游不可用时显示未完成并可重试。
- 在线或离线节点被吊销后，旧身份不能自动恢复接入；重新注册获得新序列号，旧档案保留。

## 14. 通信凭据与初始化清理讨论

以下为新增建议，尚待确认。

### 14.1 初始化后通信

本节为未来候选方案，当前不实现采集通信。最新建议是 HTTPS + Ed25519 挑战认证 + 短期会话令牌，细节见独立采集草稿；以下逐请求签名和长期令牌保留为备选讨论。初始化恢复认证独立确定。

- 如需自有采集，建议每台设备在首次启动后本地生成独立 Ed25519 密钥对，私钥保存于 `/data` 并限制权限，中心仅保存公钥和凭据状态。不得将密钥对预置在克隆镜像中。
- 对分钟级或秒级的少量上报，预计签名开销不是主要瓶颈，具体在目标硬件验证；不预设未经实测的耗时或吞吐量。
- 使用成熟密码库与标准签名格式。若使用 HTTP 请求签名，需覆盖方法、目标、请求体摘要及防重放参数，并验证时间窗口、nonce 等；具体协议另行设计。HTTPS 仍然必须使用。
- 也可采用每节点独立的 32 字节安全随机 Bearer Token，经 HTTPS 上报，中心只存令牌摘要。该方案更简单，但持有令牌即可冒充对应设备；不得多节点共用一个长期令牌。
- Ed25519 的优势是中心不保有可直接冒充节点的私钥；设备私钥被复制后仍可被冒充。两种方案均需凭据吊销、轮换和权限限制。
- 此凭据仅用于自有中心接口，不复用 Tailscale、MeshAgent 或 SSH 的密钥。

### 14.2 外地刷机与初始化授权

- 不依赖人员所在国家或固定来源 IP 作为主要注册授权。
- 激活文件支持可自定义期限和注册次数，两者均可无限；早期采用无限期、无限次数批量文件以复用镜像，中心仍支持撤销。
- 每台设备的注册记录绑定自己的公钥或请求身份，相同设备可恢复；批量令牌本身不绑定单台设备。
- 文件被复制即可按其权限继续注册，本机删除不能撤销其他副本；不把“已从节点删除”误记为“全局已吊销”。
- 不恢复旧档案；需要重建身份时用有效初始化授权注册新节点，旧档案保留。已有身份只用于正常连接和未完成初始化的恢复，不因 `/data` 未保留就自动创建新身份。

### 14.3 清理与 OverlayFS 生效顺序

以 2.3 和 6.0 为准：根目录持久可写阶段建立本机身份，注册完成并验证后删除初始化凭据、初始化脚本或程序与首次启动服务，再启用 OverlayFS 并重启。建议在独立节点认证与恢复能力确认有效后提前删除本机激活文件；如恢复认证尚不可用，则不能提前删除。

清理可重试，最终化不能因中途断电陷入无法继续的状态。重启验证方式独立安排，不保留带激活秘密的完整初始化服务。凭据放 `/data` 可避免根目录 OverlayFS 对删除结果的影响，但不能替代注册授权控制，也不改变服务凭据默认保存在根目录的决定。删除不保证擦除闪存历史或其他镜像副本；批量授权按中心配置持续有效，直到到期、耗尽或撤销。
